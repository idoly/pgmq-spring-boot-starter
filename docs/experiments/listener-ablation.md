# Listener 优化消融实验

实验对象：`f3d5250`，比较基线：`1c30942`。实验在独立源码副本中进行，没有回退当前分支或修改生产代码。

## 方法与边界

使用现有 Eclipse Temurin 25 容器、Maven 3.9.14、Spring Boot 3.5.0，以 Java 17 release 编译。
每个实验组独立构建并运行相同的单元测试。核心比较组加强了并发确认测试：归档 SQL 阻塞时，
启动第二个确认调用，观察它是否提前执行删除 SQL。最终保留的测试还等待第二个调用线程开始尝试。

运行命令：

```shell
mvn -B --no-transfer-progress '-Dtest=*,!PgmqListenerIntegrationTest,!PgmqTemplateTest' test
```

这是行为和结构的消融实验，没有测量吞吐、延迟、CPU、内存或真实 JDBC 连接竞争。
两组依赖 PostgreSQL 的集成测试没有执行。通过单元测试不能推导生产负载下的性能收益。

## 结果

| 实验组 | 单一变化 | 测试数 | 失败 | 错误 | 结果 |
| --- | --- | ---: | ---: | ---: | --- |
| baseline | 保留当前实现 | 57 | 0 | 0 | 通过 |
| no-run-isolation | 恢复旧容器生命周期实现，保留诊断所需的数据源访问和自动 ACK 复用 | 57 | 2 | 0 | 停止后释放许可空指针；重启后容量污染 |
| no-ack-fix | ACK 恢复旧的提前标记完成实现 | 57 | 2 | 0 | SQL 未完成即报告完成；失败后无法重试 |
| no-ack-serialization | 只移除三个确认方法的 `synchronized` | 57 | 1 | 0 | 两个完成操作可以重叠执行 SQL |
| atomic-reset-ack | 使用旧 CAS 实现，并在异常时重置完成标志 | 57 | 1 | 0 | 失败重试恢复，但 SQL 进行中仍报告已完成 |
| local-capture-isolation | 保留运行隔离语义，删除 `RunState`，通过局部引用传递状态、许可和执行器 | 57 | 0 | 0 | 行为保持，但没有减少代码或状态管理负担 |
| no-diagnostics | 移除诊断组件、注册和专用数据源访问器 | 54 | 0 | 0 | 其余消费、生命周期和 ACK 测试通过 |

诊断消融组同时移除了三个专用诊断测试及自动配置测试中对应的 Bean 存在性断言，
所以它与基线不是同一套 57 项测试。该组只说明其余受测行为不依赖诊断，不能把数量差异视为性能或质量提升。

## 运行隔离：保留行为，也保留目前的聚合结构

移除隔离后，`lateTaskCompletionIsIsolatedFromStopAndRestart` 的两个参数场景失败：

- 停机后，旧任务释放已被置空的 `inFlightPermits`，出现 `NullPointerException`。
- 重启后，旧任务释放到新运行的信号量，触发额外轮询，突破新运行的容量约束。

这证明需要的是“任务引用其所属运行的资源”，并不证明必须使用名为 `RunState` 的类。
因此另做了局部引用替代组：

- 用四个容器字段保存当前 active flag、许可、poll executor 和 consumer executor。
- 每轮启动创建独立的 flag 和许可，把本轮 consumer executor 捕获到局部变量。
- `pollLoop` 显式接收 flag、许可和 consumer executor；`process` 显式接收许可。
- 启动失败和停止时分别清理四个当前字段；旧任务继续使用捕获的原引用。

替代组 57 项测试通过，但两个版本的容器都是 **380 行**，生产 Java 总行数也相同。
行数只是辅助证据；实际取舍是替代组增加了字段间协调、清理赋值和参数传递。
当前 `RunState` 将同一生命周期的资源放在一起，便于检查任务归属，保留有明确收益。

## ACK：保留成功后发布完成状态和串行确认

旧 ACK 在 SQL 调用前执行 CAS，数据库异常后仍为完成状态。恢复旧实现后，失败重试和
进行中状态的测试均失败。

“保留 CAS，异常时重置”使生产 Java 总行数从基线的 4674 行增至 4688 行，仍未满足
SQL 成功返回前 `isCompleted()` 为 false 的契约。该方案还会让重叠调用在首次 SQL
进行中直接跳过；异常后首次操作未完成，已跳过的调用也不会自动重试。

只移除同步则允许第二个操作在首次 SQL 阻塞期间执行。当前方案用每个消息句柄自己的锁，
在 SQL 成功返回后发布完成状态，满足已测试的失败与并发语义。无需为此新增策略或状态机层级。

## 发现的测试缺口及保留改动

对删除同步的实现，使用提交 `f3d5250` 中未经加强的 `DefaultPgmqAcknowledgmentTest`
连续执行五次：**四次失败，一次全部通过**。原测试提交第二个任务后立即释放第一个 SQL，
可能没有形成有效重叠，因而存在漏检。

本轮只保留了测试补强：

1. 用 latch 等待第二个线程开始尝试确认。
2. 在首次归档 SQL 保持阻塞时，检查删除 SQL 在观察窗口内没有开始。
3. 释放归档，再确认只有第一个成功操作生效。

最终版本在当前实现与移除同步组重新执行完整单元测试，分别为 57 项通过和 1 项预期失败。
这里使用有界等待观察并发行为；有限次数运行不构成对所有线程调度的数学证明。

## 连接预算诊断：辅助功能，可作为精简候选

移除诊断可以减少 **1 个生产类、117 行生产 Java**，并去掉以下关联：

- 自动配置中的诊断 Bean。
- 容器仅为诊断暴露的 `getDataSource()`。
- 对上下文刷新事件、数据源包装解包和 `maximumPoolSize` 属性读取的维护。

损失是启动时的数据源预算汇总和提示，消费逻辑本身没有在测试中退化。现有诊断测试证实它能
输出预算、按池聚合且不借连接；没有证据表明它改善了实际吞吐或防止了生产故障。

若下一步目标是精简依赖和公共 API，诊断是优先删除或改为显式启用的候选，预算配置文档可以保留。
若目标是减少使用者配置错误，则可以保留为辅助能力，但应与性能优化分开评价。本次没有据此删除已交付功能。

## 最终判断

保留运行隔离、`RunState` 和 ACK 修复。当前没有证据支持用局部引用或 CAS 回滚方案替换它们。
诊断属于可取舍的使用体验功能，不能归为性能改善。保留加强后的并发回归测试。

实验容器、临时源码、原始日志和临时脚本在记录结果后清理；保留本报告和测试改动，未提交。

## 后续精简落实

根据精简目标，已移除连接预算诊断类、Bean 注册、仅供诊断使用的数据源访问器，以及专用测试。
保留连接预算配置文档、运行隔离和 ACK 修复。精简后 54 项单元测试及 Javadoc 构建通过。
上述实验表格记录的是消融时的各组结果，不代表当前仍保留诊断组件。

线程与连接路径检查还确认了验证边界：线程中断不等于 JDBC 查询取消，SQL 长轮询期限不能
约束单条语句内的锁等待；监听器允许的零秒轮询也存在高频空轮询风险。精简阶段先记录这些
边界，随后的修复和真实数据库验证如下。

## 后续零秒轮询修复与 Spring 接入验证

验证环境为独立临时 PostgreSQL 18.4 实例、Windows JDK 25.0.2，以 Java 17 release 编译。
分别使用项目的 Spring Boot 3.5.0、4.0.0、4.1.0 配置，每个配置均执行清理后的 `verify`：
**66 项测试通过、0 失败、0 错误、0 跳过，Javadoc 和打包通过**。其中每组包含 8 项真实 JDBC 测试。
原有依赖 pg_partman 镜像的两个集成测试类没有在此次执行。

| 真实数据库场景 | 已观察或验证的行为 |
| --- | --- |
| 四种模式的零秒轮询 | 立即读取可见消息，复用对应的普通 read 方法 |
| 零秒空轮询 | 数据库调用之间至少保留配置的等待间隔，避免空转 |
| 两监听器共享两条连接 | 六条消息完成处理与归档，连接总数不超过二 |
| 单连接池被占满 | 按配置的 250ms 获取超时失败，而非无限等待 |
| 慢 SQL 与查询超时 | `pg_sleep(5)` 被 1 秒查询超时取消，服务端 SQLState 为 `57014`，连接可继续查询 |
| 查询超时与正常停机 | 阻塞轮询在超时后退出，执行器结束，活动连接释放 |
| 零等待立即停机 | 线程中断后仍观察到活动 SQL；随后随长轮询期限结束退出 |
| Spring 事务代理 | 监听器确实经过事务代理，业务写入与手动 ACK 在异常时一起回滚 |

额外单元测试验证了占位符解析、自定义容器工厂、关闭监听器开关、启动失败回收，以及某个
容器停止失败后仍继续停止其余容器。

生产修改保持局部：

- 四种长轮询方法在时长为零时委托普通读取；容器只在空结果时按轮询间隔等待。
- 六个监听器 Bean 共用一个内部配置组的启用条件，保留 Bean 名称和工厂扩展入口。
- 注册中心在启动失败时回收容器，在停止失败时继续清理其余容器；以 volatile boolean
  替代已受同步方法保护的原子状态。
- 继续使用 JDK 执行器和现有数据源，没有新增生产依赖、调度框架或连接池。

这些是确定场景的行为验证，不是吞吐或容量基准，也没有模拟网络断开。立即停机不等于立即
取消 SQL 的边界仍然成立；应配置适合业务的 JDBC 查询与网络超时。测试类通过
`PGMQ_TEST_JDBC_URL` 显式启用，运行方式见 `docs/listener-tuning.md`。
